# Prototype scope and screen inventory

Established Phase 1 scope: marketing, onboarding/wallet UI, amount-specific merchant requests/QR, scan/review/authorization, shared simulation, history/receipts, dashboard, basic admin and architecture/roadmap. Optional testnet is outside the baseline. Exclusions in docs/00_PRODUCT_VISION.md apply to every screen.

## Screen contracts

Proposed inventory; screens may be panels/routes rather than separate pages. `L/E/S/F` below means loading / empty / success / failure. Static screens render immediately; their empty/error states concern optional assets or navigation. Every app screen shows “Simulation — no real money”, synthetic identity and accessible status text. Amounts use DEMO; INR, where shown, is labelled illustrative. UI foundations may use fixtures; shared behavior becomes authoritative only in Milestone 2.

## Scope choices

Marketing is a public demo explanation, not a fabricated operating service. No email collection or integration promises. Native app, production authentication, notification delivery, refunds UI, exports beyond browser print, asset selection and multi-currency requests are not baseline deliverables. Failure injection is a demo control, not arbitrary admin modification of payments. Browser printing is a proposed convenience, not tax-invoice generation.

Milestone 1 delivery note: the screen contracts above describe the full simulated prototype target. Current marketing/customer/merchant screens are fixture foundations; canonical data, idempotency, live expiry and camera QR decoding are deferred to M2. Native camera preview/feature detection is implemented, explicitly labelled as not a scanner. Admin screens remain M3. See docs/13 for implemented routes and precise limitations.
